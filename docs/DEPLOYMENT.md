# Deploying to a live URL

The goal is one URL that serves both the API and the built client, backed by a
MongoDB that can run transactions. Two things make that simpler than it sounds:

- **`SERVE_CLIENT=true`** (the default when `NODE_ENV=production`) makes the API
  process host the built SPA, so there is no second service and no CORS
  configuration between them.
- **Everything is ordinary Node and MongoDB.** No build step at runtime, no
  framework-specific platform requirements.

The deployment path below is **Render + MongoDB Atlas**, which is fully
verified and zero-config using the checked-in blueprint.

---

## 0. What you need

| Thing | Why |
|---|---|
| MongoDB Atlas account (free M0) | See the replica-set requirement below. |
| A Git host account (GitHub/GitLab) | Render deploys from a repository. |
| A Render account (free tier) | Or any host that runs a Node process. |
| Node 20.19+ locally | Only to seed the live database and to run tests. |

### Why the database *must* be a replica set

This is the single most common way this deployment fails, so it is worth stating
plainly: **MongoDB standalone servers cannot run multi-document transactions**,
and the checkout path reserves stock across multiple products inside one
transaction. A standalone `mongod` will accept the connection and then fail every
multi-line checkout with `Transaction numbers are only allowed on a replica set
member or mongos`.

Atlas clusters are replica sets by definition, including the free M0 tier, so
using Atlas removes the problem entirely. If you self-host, start `mongod` with
`--replSet rs0` and run `rs.initiate()` once — which is exactly what
`npm run dev:db` and `docker-compose.yml` do locally.

## 1. MongoDB Atlas

1. Create a free **M0** cluster.
2. **Database Access** → add a user with *Read and write to any database*.
3. **Network Access** → add `0.0.0.0/0` (allow from anywhere).
   For a demonstration this is the pragmatic choice; for anything real, restrict
   it to your host's egress addresses.
4. **Connect** → *Drivers* → copy the connection string and add the database
   name to the path:

   ```
   mongodb+srv://USER:PASSWORD@cluster0.xxxxx.mongodb.net/orders?retryWrites=true&w=majority
   ```

   The `/orders` part matters: the application reads the database name from the
   URI, and dropping it silently lands you in a database called `test`.

Confirm it works before going further — it is much easier to debug here than
through a hosting dashboard:

```bash
export MONGODB_URI="mongodb+srv://.../orders?retryWrites=true&w=majority"
npm run seed:demo          # writes the catalogue and order history
npm run start --workspace server
curl -s localhost:4000/healthz
```

## 2. Deploy

### Render (blueprint)

`render.yaml` in the repository root is a
[blueprint](https://render.com/docs/blueprint-spec): connect the repository in
Render and it creates the service, prompts for `MONGODB_URI`, and generates the
two secrets.

Set by the blueprint:

| Variable | Value |
|---|---|
| `NODE_ENV` | `production` (so `SERVE_CLIENT` defaults to on) |
| `SERVE_CLIENT` | `true` |
| `MONGODB_URI` | your Atlas URI (prompted; never committed) |
| `JWT_SECRET` | generated by Render |
| `WEBHOOK_SECRET` | generated by Render |
| `MONGOMS_DISABLE_POSTINSTALL` | `true` — skips a test-only binary download at build time |

The build command is:

```
npm ci --include=dev && npm run build && npm run seed:demo
```

Three notes on that line:

- `--include=dev` is required. Vite is a dev dependency, and a bare `npm ci`
  under `NODE_ENV=production` would skip it and fail the client build.
- `npm run seed:demo` **replaces** orders, payments and claims on every deploy.
  That is right for a demo (a reviewer always lands on fresh, consistent data) and
  wrong for a product — delete that step to keep data across deploys.
- The seeding step needs `MONGODB_URI` at build time, which the blueprint
  provides.

### Any other Node host

The equivalent settings are:

```
Build:  npm ci --include=dev && npm run build && npm run seed:demo
Start:  npm start                      # node server/src/server.js
Health: /healthz
```

Platforms that run a long-lived process (Railway, Fly, Heroku, a VM, or
`systemd`) all work with those three lines. Serverless platforms do **not**: the
reaper is a background interval, the connection is pooled, and graceful shutdown
drains in-flight checkouts.

### Deploying the client separately (optional)

If you would rather serve the SPA from a CDN, set `SERVE_CLIENT=false`, host
`client/dist` on the static host of your choice, and set `CORS_ORIGINS` on the
API to that origin. The API is then the only thing that needs a Node host.

## 3. Post-deploy verification

Run these in order. Each one fails loudly if the step before it was wrong.

```bash
BASE=https://your-service.onrender.com

# 1. Liveness, and that the process can reach the database.
curl -s $BASE/healthz

# 2. The API is serving, not just the process.
curl -s $BASE/api/products | head -c 200

# 3. The SPA is served by the same origin, not a 404 page.
curl -s -o /dev/null -w '%{http_code} %{content_type}\n' $BASE/

# 4. An unknown API path returns the API's JSON error envelope, NOT index.html.
#    (This is the check that catches a too-greedy SPA fallback.)
curl -s $BASE/api/does-not-exist
```

Then in a browser:

1. **Catalogue** loads with the seeded products and stock figures.
2. **Sign in** as `admin@shop.test` / `password1234`.
3. **Operations console** → the invariant badge reads *All invariants hold*, and
   the reconciliation report lists no problems. This is the end-to-end proof that
   the seeded data satisfies I1–I7 on the live database.
4. **Concurrency Lab** → set stock to 10, fire 200 buyers: 10 confirmed, 190
   rejected, `available: 0`, invariants still clean.
5. **Buy something** as `shopper@shop.test`, then open **Orders** and watch the
   awaiting-payment order settle.

### Two behaviours that look like bugs and are not

- **Free-tier cold start.** A sleeping instance takes ~30 s to answer the first
  request. The health check warms it.
- **Open orders expire.** A `pending_payment` order holds stock until its
  reservation TTL lapses (15 minutes by default; `docker-compose.yml` raises it to
  an hour for demos). After that the reaper reclaims the stock and the order
  becomes `expired`. That is the leak-prevention mechanism working, not data
  corruption — re-run `npm run seed:demo` for a fresh set.

## 4. Operating notes

- **Secrets.** `JWT_SECRET` and `WEBHOOK_SECRET` must be set per environment and
  never committed; the boot validator rejects a `JWT_SECRET` shorter than 16
  characters. Rotating `JWT_SECRET` invalidates existing sessions, which is the
  intended effect.
- **Scaling.** Two instances are safe: idempotency claims, inventory counters and
  the payment lease are all database-arbitrated, so nothing depends on being the
  only process. The reaper becomes duplicated work rather than a correctness
  problem, because every claim it takes is conditional.
- **Logging.** Structured JSON on stdout, one line per request, with a request id
  that also appears in error responses. Your platform's log search is the
  intended consumer.
- **Cost.** Free Atlas M0 plus a free Render instance is enough for review. The
  Concurrency Lab is the heaviest thing in the app (200 concurrent checkouts);
  it is a demonstration tool, not a load test.
- **Teardown.** Nothing is written outside MongoDB and the platform's own logs.
  Deleting the service and the cluster removes everything.
